### How snp actually replaces an installed Python pre-commit, and how the two coexist
- target: /tmp/claude-1000/-home-dromix-projects-snp/484ec4f1-c0f7-4123-b7cd-bc3e3cb59b63/scratchpad/research/11-dropin-migration.md
- why: The user asked for an in-place replacement, but no doc says how the swap physically happens or what a user sees on the first commit afterwards. Existing hook scripts (resources/hook-tmpl) run `exec "$INSTALL_PYTHON" -mpre_commit` first. While the old pipx/venv python still exists, Python pre-commit keeps running after snp is installed, and nothing warns the user. Configs and tools also call `pre-commit …` by name: `entry: pre-commit hazmat …`, `python -m pre_commit`, tox, Makefiles, and the official GitHub action. Checked via WebFetch: the action runs `python -m pip install pre-commit`, caches `~/.cache/pre-commit` with key `pre-commit-3|${pythonLocation}|hashFiles('.pre-commit-config.yaml')`, and runs `pre-commit run --show-diff-on-failure --color=always --all-files`. The related decisions are open questions spread across 01/02/03/06/07/10 and some contradict each other: store location and PRE_COMMIT_HOME, --version string, branding, shim hash, PyPI name (`snp` is taken).

### `pre-commit hazmat` run from a hook entry: actual semantics (doc 03 §15 is wrong)
- target: /tmp/claude-1000/-home-dromix-projects-snp/484ec4f1-c0f7-4123-b7cd-bc3e3cb59b63/scratchpad/research/03-install-store-commands.md
- why: lang_base.hook_cmd (lang_base.py:174-178) rewrites `pre-commit hazmat …` to `sys.executable -m pre_commit.commands.hazmat`. That runs hazmat.main() directly, so there is no error_handler, no Store and no logging handler. I verified on 4.6.2 that a missing executable then produces a full Python traceback in the hook output with `- exit code: 1`. Doc 03 §15 says exit 3. Argparse errors inside hooks use prog `hazmat.py` with exit 2: `usage: hazmat.py cd [-h] subdir ...` / `hazmat.py cd: error: the following arguments are required: subdir, cmd`, and `hazmat.py: error: argument tool: invalid choice: 'bogus' (choose from 'cd', 'ignore-exit-code', 'n1')`. The rewrite matches tokens after shlex, so `'pre-commit' hazmat …` is also rewritten (verified). Invoking `pre-commit hazmat` directly with no tool crashes with `An unexpected error has occurred: AttributeError: 'Namespace' object has no attribute 'cmd'` (exit 3). None of this is in the docs, and snp's rewrite to `[current_exe, 'hazmat', …]` must reproduce the in-hook behaviour, not the CLI behaviour.

### CLI surface parity: verbatim help, usage and argparse error routing
- target: /tmp/claude-1000/-home-dromix-projects-snp/484ec4f1-c0f7-4123-b7cd-bc3e3cb59b63/scratchpad/research/12-cli-surface.md
- why: Only `validate-config --help` is captured verbatim (01 §8.1). The top-level help, each subcommand's help and the usage lines are not. The docs also get the error routing partly wrong. Verified on 4.6.2: `pre-commit run --bogus` is reported by the top-level parser (top-level `usage: pre-commit [-h] [-V] {…}` plus `pre-commit: error: unrecognized arguments: --bogus`), not `pre-commit run: error:` as 02 §2.2 generalises. `PRE_COMMIT_COLOR=bogus` is only an error when `--color` is not given (`PRE_COMMIT_COLOR=bogus pre-commit sample-config --color never` exits 0); 02 §2.2 and 03 §1.1 say it always errors. Scripts and wrappers depend on exit codes and stderr text, and clap's defaults differ in format, prefix matching and env-default handling.

### One catalog of uncaught-exception (exit 3) paths and secondary messages, with a keep-or-fix decision for each
- target: /tmp/claude-1000/-home-dromix-projects-snp/484ec4f1-c0f7-4123-b7cd-bc3e3cb59b63/scratchpad/research/13-crash-and-message-catalog.md
- why: Only config-time crashes are catalogued (01 §16). Others are scattered or missing. Some I verified on 4.6.2: `files: 'a{4294967296}'` gives `An unexpected error has occurred: OverflowError: the repetition number is too large` (exit 3), because cfgv.check_regex catches only re.error (cfgv.py:384-388). `files: '[[]'` passes but prints `…/cfgv.py:386: FutureWarning: Possible nested set at position 1` plus `  re.compile(v)` on stderr. Others are unverified but visible in the source. pre-push uses `subprocess.check_output`/`call` (hook_impl.py:116-164), whose CalledProcessError str is `Command '(…)' returned non-zero exit status N.`, unlike util.CalledProcessError's `command:/return code:/stdout:/stderr:` block, and its stderr is not captured. A deeply nested regex can raise RecursionError. `make_local` logs `Initializing environment for local.` (or `local:dep1,dep2.`; store.py:160,212-215), which no doc quotes. snp needs a list of exact first lines and a policy for each case.

### Pick one regex engine using corpus evidence, and set Python `re` acceptance parity for config patterns
- target: /tmp/claude-1000/-home-dromix-projects-snp/484ec4f1-c0f7-4123-b7cd-bc3e3cb59b63/scratchpad/research/01-config-schema.md
- why: The docs disagree. 01 §13/§18 and 04a §12.3 propose a two-tier design (regex fast path, fancy-regex fallback); 07 D4 picks fancy-regex as the single engine; 10 Q6 defers the choice. The acceptance edge cases are also incomplete. Config patterns are `str` (Unicode) regexes and pygrep patterns are bytes regexes, so they need different translators. Python raises OverflowError rather than re.error for huge repeat counts, which pre-commit turns into exit 3. `(?x)` verbose patterns in block scalars are common. The `$`-before-final-newline and `\Z` translations must be the same in both modes. Implementers need one decision and one translator spec.

### Windows and macOS behaviour that is only derived, never verified: list it and plan the checks
- target: /tmp/claude-1000/-home-dromix-projects-snp/484ec4f1-c0f7-4123-b7cd-bc3e3cb59b63/scratchpad/research/14-platform-matrix.md
- why: Every observation was made on Linux. Several Windows claims are marked "derived" or have no evidence: the hook script written in text mode, so CRLF (03 §2.4/§18), and how Git for Windows sh runs it; `os.access(X_OK)` being true for every file, which makes every file `executable` and triggers shebang parsing for extension-less files (08 §4.3); `msvcrt.locking` region 0xffff vs Rust File::lock (LockFileEx) interop (07 D7); unsigned NTSTATUS exit codes in `- exit code:` (10 Q13); `[WinError N]` text; BatBadBut InvalidInput for .cmd shims (04a §14.6); VT enabling on stderr for colour; `relpath` across drives. On macOS: `/tmp` realpath and NFD/precomposeunicode filenames from git. A drop-in tool that is wrong on Windows breaks a large user base.

### Git version floor, git feature matrix, git ≥2.54 config-based hook invocation, and how user git config affects pre-commit's own git calls
- target: /tmp/claude-1000/-home-dromix-projects-snp/484ec4f1-c0f7-4123-b7cd-bc3e3cb59b63/scratchpad/research/02-run-pipeline.md
- why: pre-commit 4.6.2 depends on git features with different minimum versions. Examples: `ls-files --deduplicate` (2.31, git.py:155), `cat-file -e <sha>^{commit}`, `--filter=blob:none` with extensions.partialClone (autoupdate.py:49-53), `protocol.version=2` shallow fetch of a SHA, `-c submodule.recurse=0`, and the git 2.54 `hook.<name>.command` mode. No doc says what snp requires or what it does on older git. 02 Q13 even leaves open whether git 2.54 passes `--`, which decides whether hook-impl's `rest[1:]` drops the right token. lefthook enforces a 2.31 minimum (internal/git/repo.go:20). User config can change the output of pre-commit's own git calls: diff.renames for the non-`-z` callers in pre-commit-hooks, color.ui, diff.noprefix, core.quotePath, status settings, and fsmonitor. Partial notes exist in 09 §3 and 10 Q8 but nothing is consolidated for the run pipeline.

### One Python-stdlib semantics shim spec with test vectors (splitlines, split/rsplit/strip whitespace, os.path, shlex.quote/join, repr)
- target: /tmp/claude-1000/-home-dromix-projects-snp/484ec4f1-c0f7-4123-b7cd-bc3e3cb59b63/scratchpad/research/15-python-semantics-shims.md
- why: Byte-compat depends on Python string and path semantics that are specified only in pieces. `stdin.decode().splitlines()` plus `line.rsplit(maxsplit=3)` in pre-push (hook_impl.py:128-130) splits on \r, \x0b, \x0c, \x1c-\x1e, \x85,   and  , and rsplit uses Unicode whitespace. Doc 03 §20.4 instead proposes splitting on \n and stripping \r. Other cases: `parse_merge_msg_for_conflicts` uses bytes.splitlines; autoupdate `_original_lines` uses splitlines(True) together with REV_LINE_RE `\s`; SKIP uses str.strip; `os.path.normpath`, `relpath`, `abspath`, `commonpath`, `realpath` and `expanduser` behave differently on POSIX and Windows (config display path, --files, exe_exists, init-templatedir); `shlex.quote`/`join` are used in hook scripts and messages; repr is used for lists and tuples in hook-impl and lang_base messages. Each Rust port needs exact vectors, or snp diverges silently.

## Contradictions (MUST be resolved explicitly by the design)

1. Hook stdin. 02 §21.3 ('stdin(Stdio::null())') and 06 §8 ('stdin Stdio::null()') contradict 04a §14.3, which says to use Stdio::piped() and drop ChildStdin, i.e. an empty pipe and not /dev/null. 02's own TL;DR #9 says 'closed pipe, or /dev/null in color mode'. Source: util.py:81-113 sets stdin=PIPE and communicate() closes it (non-color); util.py:176-178 uses /dev/null for the pty path. 04a and the 02 TL;DR are correct; 02 §21.3 and 06 §8 are wrong.

2. YAML error-text parity. 01 §18.2 and 07 D3 say libyaml-safer reproduces PyYAML CSafeLoader messages byte for byte and require it. 03 §13 says YAML parse error texts 'cannot be byte-identical in Rust. Golden tests should compare the structure only'. 10 §6 item 7 makes YAML error bodies Tier B (free-form).

3. Regex engine. 01 §13/§18.1 and 04a §12.3 recommend two tiers (the `regex` crate fast path, fancy-regex for backtracking features). 07 D4 picks fancy-regex 0.19.2 as the single engine. 10 Q6 says to decide after running a corpus.

4. Async runtime. 02 §21.4 says no async runtime is needed for the run path (std::thread::scope plus an AtomicUsize work queue). 06 §8 says tokio current-thread is sufficient. 07 D6/D8 select tokio 1.53 multi-thread with spawn_blocking for ureq and locks (07 §3 lock algorithm uses spawn_blocking).

5. Toolchain pin. 07 D1 pins the toolchain to 1.99.0 with MSRV 1.98. 10 §0/§7 says snp MUST ship rust-toolchain.toml with channel = "1.98.0". The task specifies rustc 1.98.0.

6. hazmat failure exit code. 03 §15 says normalize_cmd errors (ExecutableNotFoundError) 'surface as exit 3'. In the documented hook-entry path, hook_cmd rewrites to `python -m pre_commit.commands.hazmat`, which has no error_handler. Verified on 4.6.2: a full Python traceback and `- exit code: 1`. Argparse errors there exit 2 with prog `hazmat.py`. Exit 3 applies only to a direct `pre-commit hazmat …` CLI call.

7. PRE_COMMIT_COLOR. 02 §2.2 ('Invalid value or invalid env value → exit 2') and 03 §1.1 ('An invalid value (even from the env var) gives the argparse error') are imprecise. Verified on 4.6.2: the env default is only converted when --color is absent, so `PRE_COMMIT_COLOR=bogus pre-commit sample-config --color never` exits 0. An empty or bogus value errors only when the flag is not given.

8. Argparse error prefix. 02 §2.2 says usage errors print `pre-commit run: error: <msg>`. Unrecognized arguments are actually reported by the top-level parser with the top-level usage and `pre-commit: error: unrecognized arguments: --bogus` (verified on 4.6.2, exit 2). 10 CLI-07 has the correct form.

9. Env-dir naming. 03 §20.5 item 9 uses `<ENV_DIR>-<version>` only when the version matches ^[A-Za-z0-9._+-]{1,64}$ and otherwise `<ENV_DIR>-h<hash>`. 04a §14.2 keeps the literal pre-commit naming (nested dirs for absolute python paths 'still works') and rejects only versions whose normalized path leaves the prefix.

10. Install-state files. 03 §20.5 item 8 writes only `<env>/.snp-install-state.json`. 04a §11.4 step 7 and §14.9 write `<envdir>/.snp_state.json` (different name) and also pre-commit's `.install_state_v1` and `.install_state_v2`.

11. Store location and PRE_COMMIT_HOME. 03 §20.5 says SNP_HOME, then $XDG_CACHE_HOME/snp, then ~/.cache/snp, never sharing db.db or env dirs (PRE_COMMIT_HOME interplay left open). 10 Q5 says a separate default store but 'honor PRE_COMMIT_HOME exactly', which would put snp's layout inside pre-commit's directory. 06 §8 reads PRE_COMMIT_HOME only for clean/gc. 04a §14.10 assumes a possibly shared store where snp must also take pre-commit's `<store>/.lock`.

12. Crash log. 03 §20.5 item 13 says `<store>/snp.log`. 02 open question 7 leaves the shared `$PRE_COMMIT_HOME/pre-commit.log` open. 10 Q9 says keep pre-commit's log skeleton.

13. Executable lookup. 04a §14.18 says do not use the `which` crate, because it has the wrong semantics for relative PATH entries, empty entries and dir-major PATHEXT. 06 §8 says 'Windows command resolution: PATHEXT via `which`'.

14. CPU count. 02 §21.4 and 04a §14.4 require sched_getaffinity for parity. 03 §20.6 uses std::thread::available_parallelism for `autoupdate -j 0`, but pre-commit uses xargs.cpu_count(), which is sched_getaffinity (autoupdate.py:187).

15. fsmonitor flag. 06 §8 proposes a GitCmd builder that always adds `-c core.useBuiltinFSMonitor=false`. pre-commit adds it only in init_repo, get_best_candidate_tag and autoupdate (git.py:129,302,353; autoupdate.py:40). 03 §20.2 says store and autoupdate commands only.

16. Stash restore algorithm. 02 §21.10 keeps pre-commit's exact restore (git apply, retry with core.autocrlf=false, then checkout -- . and re-apply) and adds only fsync and O_EXCL. 06 §7 item 9 and §8 propose a different restore: restore the index from the captured tree with read-tree/reset, check out that tree, apply, then verify that `git diff-index --binary <tree>` equals the patch. The two give different observable git state on conflict.

17. In-process emulation granularity. 04a §12.2 says native pygrep processes all files in one pass, with no xargs partitioning; 04a Q8 notes this changes error semantics, since pre-commit aborts only the rest of a partition. 09 §0/§2.2 decides native builtin hooks run once per partition for parity. 02 §21.14 says pygrep output and partition semantics 'must match exactly'.

18. Pre-push stdin parsing. 03 §20.4 proposes splitting on `\n`, stripping `\r`, and splitting fields with rsplitn(4, ' ') over ASCII whitespace. pre-commit uses `stdin.decode().splitlines()` and `line.rsplit(maxsplit=3)` (hook_impl.py:128-130): Python splitlines (\r, \x0b, \x0c, \x1c-\x1e, \x85,  ,  ) and Unicode-whitespace rsplit. 02 §16.3 describes the Python semantics correctly. 03 also turns malformed lines into skips, where pre-commit crashes (exit 3), without marking this as a deviation in 02.
